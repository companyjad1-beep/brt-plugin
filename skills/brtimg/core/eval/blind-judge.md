# 골든셋 블라인드 교차심판 프로토콜

이 절차는 하네스 산출물이 Fable 5 골든셋과 구별되지 않는지 확인하는 `layer=golden-blind` 평가이다. 심판에게는 산출 출처를 숨기고, 각 항목이 Fable 5 산출인지 하네스 산출인지 이진 분류하게 한다.

## 0. 평가 대상 개정 (2026-07-08 실측 근거)

정식 acceptance 판정의 비교 대상은 **프롬프트 텍스트가 아니라 결과 이미지**다. 근거: 2026-07-08 정식 프롬프트 텍스트 블라인드에서 정확도 0.0000(완전 역전 식별)이 나왔고, 원인 분석 결과 최상급 크리에이터들의 프롬프트 문체가 서로 이질적(유기 서사형 vs 태그 스택형)이어서 문체 비구별성은 완성도 척도가 될 수 없음이 확인됐다. 같은 날 결과 이미지 블라인드(정규화·격리 동일 원칙)에서 정확도 0.5000으로 통과가 성립했다.

- 정식 층: **이미지 블라인드** — 크리에이터 공개 결과물 M장 vs 하네스 산출 이미지 N장(N=M=10~15). 전 장 동일 정규화(상·하단 크롭으로 워터마크·모서리 단서 제거, 동일 장변·포맷·품질, 메타데이터 제거) 후 셔플. 심판은 시각 단서만으로 이진 분류한다.
- 프롬프트 텍스트 블라인드는 문체 진단 보조 도구로 강등한다(하네스 식별 단서 탐지용). acceptance 근거로 쓰지 않는다.
- 크리에이터 이미지 수거는 하네스가 스크립트로 수행하되 하네스 컨텍스트에서 열람하지 않는다(수거·정규화·매핑 보관자와 심판 분리 원칙은 2~3절 그대로 적용).
- 정규화 결함은 판정을 오염시킨다: 1라운드에서 워터마크 잔존이 식별 단서로 작동해 0.6667이 나왔고, 크롭 보정 후 재실행에서 0.5000이 나왔다. 정규화 후 양 풀에 남는 비내용 단서(워터마크, 테두리, 해상도, 압축 흔적)가 없는지 먼저 점검한다.
- 이하 절의 "항목/본문"은 이미지 평가에서 "이미지 파일"로 읽는다. 쿼럼, 격리, 밴드(0.40~0.60), 사용자 확인, 리포트 규격은 동일하게 적용한다.

## 1. 정식 실행 전제

정식 블라인드 평가는 holdout-eval 쿼럼이 도달했을 때만 실행한다.

- 하네스 산출 수 `N`: 10~15
- holdout 골든셋 수 `M`: 10~15
- 정식 조건: `N`과 `M`이 모두 10~15 범위에 있고, 두 집합이 같은 수량으로 맞춰진 상태
- 미달 조건: 어느 한쪽이라도 10개 미만이면 정식 실행하지 않고 대기한다.

수집 공개 프롬프트나 축소 벤치로 만든 소량 비교는 잠정 진단 전용이다. 축소 벤치는 문제 탐색에는 사용할 수 있지만 acceptance 통과 근거로 인정하지 않는다.

## 2. 블라인드 번들 생성

1. 하네스 산출 `N`개와 holdout `M`개를 준비한다.
2. 번들 생성 전에 각 항목을 공통 plain text로 정규화한다. 포맷, 마크다운 장식, 메타필드, 주석, 라벨, 파일경로, 출처, 생성일, 작성자명, 저장 위치, 원본 순서를 제거해 문체 외 포맷 단서가 남지 않게 한다.
3. 남은 평가 단위에는 심판이 볼 수 있는 본문과 필요한 최소 표시 번호만 둔다.
4. 전체 `N + M`개 항목을 무작위 셔플한다.
5. 셔플 전후 매핑은 외부 매핑 파일에만 보관한다.
6. 매핑 파일은 심판에게 공개하지 않는다.

매핑 파일에는 셔플 순서, 원 출처, 원본 파일 참조, 정답 라벨을 기록할 수 있다. 단, 이 파일은 평가 번들 밖에 두고 심판 컨텍스트에 포함하지 않는다.

## 3. 심판 격리 메커니즘

심판은 하네스 구현, 스타일 라이브러리, 참고 예시, 파일 경로를 보지 않은 새 컨텍스트에서 실행한다.

역할 분리 규칙: 블라인드 번들 생성·매핑 보관자와 심판은 반드시 별개 세션 또는 별개 에이전트여야 한다. 번들 생성자가 심판 역할을 겸임하면 안 되며, 심판 세션은 정규화된 번들 파일만 수신한다.

- Claude Code: 포크 서브에이전트 또는 새 컨텍스트를 사용한다. 하네스 스킬, 스타일 라이브러리, 체크리스트 내부 경로, 작업 디렉터리 힌트를 로드하지 않는다.
- Codex: ephemeral 실행 또는 새 스레드를 사용한다. 이전 하네스 대화, 저장 경로, reference 예시를 공유하지 않는다.
- 심판 프롬프트에는 “각 항목이 Fable 5 산출인지 하네스 산출인지 분류하라”는 지시와 정규화된 번들 본문만 전달한다.
- 심판에게 하네스 산출 방식, 프롬프트 템플릿, 파일명 규칙, 수집 날짜, holdout 구성 규칙을 설명하지 않는다.

심판은 항목별로 `Fable 5` 또는 `harness` 중 하나를 고르고, 가능하면 짧은 이유를 남긴다. 이유는 분석 보조 자료일 뿐이며 정답 라벨은 매핑 파일로만 채점한다.

## 4. 판정과 합격 기준

채점자는 심판 결과를 외부 매핑 파일과 대조해 식별 정확도를 계산한다.

```text
식별 정확도 = round(정답 분류 수 / (N + M), 4)
```

기준선은 무작위 추측의 50%다. `accuracy`는 소수 4자리로 반올림해 기록하고, 합격 밴드는 반올림된 값 기준 50%±10%p, 즉 0.40 이상 0.60 이하를 경계 포함으로 비교한다.

- `accuracy < 0.40`: 밴드 밖 하방이다. 심판이 일관되게 반대로 분류했을 가능성과 라벨 매핑 오류를 우선 점검한다.
- `0.40 <= accuracy <= 0.60`: 하네스 산출이 골든셋과 쉽게 구별되지 않는 범위이므로 블라인드 관점 합격이다.
- `accuracy > 0.60`: 밴드 밖 상방이다. 하네스 산출이 식별 쉬운 상태이므로 불합격으로 보고 분석 절차를 수행한다.

밴드 밖 상방 불합격 분석 절차:

1. 정답 처리된 하네스 항목만 모아 심판 이유를 본다.
2. 반복적으로 언급된 차이를 스타일, 구도, 문장 흔적, 과도한 제약, 해상도·메타데이터 잔재, 생성기 특유 결함으로 분류한다.
3. 프롬프트 하네스의 템플릿성 문구나 산출 후처리 흔적이 식별 단서가 되었는지 확인한다.
4. 확인된 원인만 수정 대상으로 삼고, 골든셋 내용을 직접 모사하는 방향으로 수정하지 않는다.
5. 수정 후 정식 쿼럼을 다시 만족하는 새 블라인드 번들로 재평가한다.

## 5. 사용자 확인 기록

블라인드 결과를 확정하기 전에 사용자 확인을 기록한다. 형식은 다음 객체를 사용한다.

```json
{
  "verdict": "confirmed",
  "note": "정식 쿼럼과 격리 조건을 확인했고 50%±10%p 밴드 안에 있으므로 golden-blind 통과로 확인한다.",
  "timestamp": "2026-07-07T10:00:00+09:00"
}
```

`verdict`는 확인 상태를 나타내는 짧은 문자열로 기록한다. `note`에는 쿼럼, 격리, 밴드 판단에 대한 사용자 확인 메모를 남긴다. `timestamp`는 ISO 8601 문자열을 사용한다.

## 6. 평가 리포트 저장 예시

결과 파일은 `workspace/reports/` 아래에 `eval-report` 스키마로 저장한다. 예: `workspace/reports/2026-07-07-wellness-launch-golden-blind.json`

```json
{
  "schemaKind": "eval-report",
  "schemaVersion": 1,
  "id": "eval-2026-07-07-wellness-launch-golden-blind",
  "promptRef": "workspace/prompts/2026-07-07-wellness-launch.yaml",
  "layer": "golden-blind",
  "verdict": "passed",
  "blind": {
    "N": 12,
    "M": 12,
    "accuracy": 0.5417,
    "band": "50%±10%p",
    "user_confirmation": {
      "verdict": "confirmed",
      "note": "하네스 산출 12개와 holdout 골든셋 12개의 정식 쿼럼, 새 컨텍스트 심판 격리, 정확도 54.17%가 합격 밴드 안에 있음을 확인했다.",
      "timestamp": "2026-07-07T10:00:00+09:00"
    }
  },
  "createdAt": "2026-07-07T10:05:00+09:00"
}
```

`blind.N`은 하네스 산출 수, `blind.M`은 holdout 수로 기록한다. `accuracy`는 정답 분류 수를 `N + M`으로 나눈 뒤 소수 4자리로 반올림한 값이다. `band`는 반올림된 `accuracy` 기준으로 0.40 이상 0.60 이하를 경계 포함으로 비교해 기록한다.

## 7. 오염 방지 체크리스트

평가 후 아래 항목을 점검한다. 하나라도 실패하면 해당 블라인드 판정은 정식 근거로 쓰지 않는다.

- [ ] 심판이 하네스 작업 컨텍스트를 읽지 않았다.
- [ ] 번들 생성·매핑 보관자와 심판이 별개 세션 또는 별개 에이전트였다.
- [ ] 심판이 하네스 스킬, 스타일 라이브러리, 체크리스트 내부 경로를 로드하지 않았다.
- [ ] 번들에 원본 파일경로, 출처, 생성일, 작성자명, 저장 위치가 남아 있지 않았다.
- [ ] 번들링 전 포맷, 마크다운 장식, 메타필드, 주석을 제거하고 공통 plain text로 정규화했다.
- [ ] 심판 프롬프트에 reference 예시나 하네스 템플릿 설명이 포함되지 않았다.
- [ ] 외부 매핑 파일이 심판에게 공개되지 않았다.
- [ ] 심판 결과 수집 전까지 정답 라벨을 대화나 파일명으로 노출하지 않았다.
- [ ] 축소 벤치 결과를 acceptance 근거로 사용하지 않았다.
