# store-shots — 스토어 출시 자산 자동 생성

앱 프로젝트 루트에서 실행한다. 산출물은 대상 앱 프로젝트의 `store_assets/` 아래에 만든다.

**북극성 (모든 단계의 최종 판정 기준)**: 이 스킬의 산출물은 "사람들이 이 앱을 써야만 하는 이유"를 이미지로 만드는 것이다. 포인트·카피·화면·이미지 무엇이든 최종 질문은 하나 — **"이걸 본 사람이 이 앱을 깔아야 할 이유가 여기 있는가?"** 앱의 특징(속성) 나열은 답이 아니다. 특징과 이유를 구분하라: "다정한 반말로"(특징·톤) ❌ vs "내 얘기를 진짜 읽고 콕 짚어줘"(경쟁 AI가 못 주는 가치 = 이유) ⭕.

렌더러 위치(고정): `${CLAUDE_PLUGIN_ROOT}/skills/store-shots/generate.py`
의존성: Python 3.12+, `pillow`, `pyyaml` (`pip install pillow pyyaml`)

## 워크플로우

### 0. 프리플라이트 (환경·권한 확인 — 워크플로우 시작 전 1회)

캡처·생성 단계에서 막혀 되돌아오지 않도록, **시작하자마자** 아래를 한 번에 점검해 3·5단계 경로를 미리 확정하고 사용자에게 한 줄로 확인받는다.

1. **codex 연결 확인** — `codex --version`(또는 `codex exec` 헬스체크). 되면 5단계 배경·개념 이미지를 codex 생성 경로로, 안 되면 절차적 렌더(`glow`+`stars`) 폴백으로 확정. (codex가 돼도 배경이 소품·사진급 연출일 때만 실제 생성 — 5단계 결정 규칙.)
2. **캡처 대상 확인 (3단계 경로 선결정)** — `adb devices`로 점검:
   - **테스트 폰이 연결돼 있으면** → 실기기에 debug 빌드(`flutter run` / `flutter build apk --debug` + 설치) 후 실기기 캡처.
   - **없으면 에뮬레이터** 부팅(`flutter emulators --launch <id>` / `emulator -list-avds`)해서 캡처.
   - `adb` 자체가 없거나 기기·에뮬 모두 불가면 → 실기기 연결 또는 수동 캡처를 사용자에게 요청. iOS 실캡처는 Mac 전용(`xcrun simctl`) 고지.
3. **데모 데이터 주입 동의 (주입 전 필수 확인)** — 캡처할 화면이 비어 있거나(식당 0·기록 0 등) 데모가 필요하면, 주입 **전에** 사용자에게 물어 확정한다: ⓐ 어디에? — 로컬 DB 스왑(sqlite) / **별도 데모 전용 백엔드 프로젝트** / 로컬 인스턴스(예: `supabase start`). **프로덕션·실사용자 DB엔 절대 주입 금지** — 원격 백엔드(Supabase 등) 앱이면 반드시 데모 전용 프로젝트나 로컬로. ⓑ debug 빌드에만. 동의 없으면 데모 단계를 건너뛰고 기존/수동 캡처 또는 화면 없는 개념 슬라이드(3단계 4번)로 진행.
4. 점검 결과(**codex 유무 · 캡처 경로 · 데모 주입 승인 여부**)를 한 줄로 요약·확정하고 1단계로 넘어간다.

### 1. 코드베이스 분석 → 마케팅 포인트 도출

- 소스 우선순위: **⓪ `docs/MARKETING.md`** (marketing-plan 스킬 산출물 — 있으면 포지셔닝·타겟·현재 대안·차별점·확정 카피가 이미 검증돼 있으므로 포인트 표 ①~③을 여기서 직접 채운다) → **① PRD/기획 문서**(`docs/`, `*.prd*`, `README`, 스펙 문서 등을 find/search로 탐색) → ② 스토어 메타데이터(기존 소개글, fastlane metadata 등) → ③ 라우트/화면 목록과 주요 기능 코드. PRD가 있으면 거기 명시된 타겟 사용자·핵심 가치를 최우선 근거로 삼는다.
- **카피 원칙 선독**: 포인트 도출 전에 `PATTERNS.md`의 "카피 원칙" 절을 읽는다 — 포인트 표가 카피의 원재료라서, 어떤 재료를 캐야 하는지 먼저 알아야 한다. (4단계에서 처음 읽으면 카피가 이미 기능 라벨로 굳은 뒤다.)
- **사용자 가치 기준**으로 마케팅 포인트 3~6개를 도출한다. 기능 나열이 아니라 "이 앱이 해결하는 문제"를 뽑아라. (예: "SQLite 동기화" ❌ → "오프라인에서도 끊김 없이" ⭕)
- 각 포인트마다 4칸을 채운다: ① **pain** — 누가 언제 겪는 문제인가 ② **해결 후 상태** — 이 앱을 쓰면 유저의 하루가 어떻게 달라지나 (기능 동작 설명 금지) ③ **대안 대비 차별** — 경쟁 앱·기존 방식(수첩·캡처·타 AI 등)은 왜 이걸 못 주나 ④ **증거 화면** — 어느 스크린/상태가 이걸 보여주나. **title/subtitle은 여기서 쓰지 않는다** — 1-b 카피 패스의 산출물이다.
- 도출한 포인트를 사용자에게 표로 보여주고 확인받는다. 이 표가 이후 모든 산출물의 단일 소스이자, 카피 감사 ⓪이 요구하는 "이유의 근거"다.

### 1-b. 카피라이팅 패스 (포인트 → 헤드라인·서브)

포인트 표 확정 후 컷별 카피를 **별도 패스**로 쓴다. 포인트 문구를 그대로 title에 옮기면 반드시 기능 라벨이 된다 — 카피는 도출의 부산물이 아니라 독립 공정이다.

1. **벤핏 사다리 2단 강제** (`PATTERNS.md` 카피 원칙 5): 포인트에 "그래서?"를 두 번 묻는다. 기능("3초 기록") → 1차: 빨리 끝남 → 2차: **부담이 없어서 매일 하게 됨** ← 이 꼭대기(유저의 달라진 상태)만 헤드라인 자격이 있다.
2. **헤드라인 = 정체성 명사구 또는 결과 훅** (카피 원칙 4): 앱이 유저에게 무엇이 되어주는지 명명하거나, 해결 후 상태를 유저 언어로. 기능명·조건문("~하면") 금지.
3. **입말화 — 판매카피식 초단문 모드** (brtwritenotai `style-presets.md` §7-b, 같은 플러그인 `skills/brtwritenotai/core/style-presets.md`): 사다리 꼭대기를 찾았어도 "~합니다" 완성문으로 쓰면 광고 티다. 서술어 버리기(명사구·부사 종결) · 유저 혼잣말 훔치기 · 장면 앵커("밤마다"·"눈 뜨면") · 대화체 단정으로 문장화하고, 서브도 같은 입말을 유지한다. 벤핏 사다리가 "무엇을", 초단문 모드가 "어떻게"다 — 이 단계를 건너뛰면 내용은 맞는데 문장이 AI다.
4. **서브 = 이유의 근거**: 헤드라인 재진술 금지. ⓐ 그게 가능한 메커니즘("탭 한 번, 입력 없음") 또는 ⓑ 포인트 표 ③의 대안 대비 차별 중 위계 높은 쪽을 쓴다. 서브가 헤드라인보다 추상적이면 실패.
5. **즉시 감사**: 컷별 확정 전에 `PATTERNS.md` "카피 감사 체크" ⓪~③ + AI티 검사(brtwritenotai 룰북 + §7-b 금지 목록)를 돌린다. 4단계 세트 QA에서 처음 걸러내면 이미 소개글·config에 전파된 뒤다.

### 2. 스토어 소개글 작성 → `store_assets/listing/<locale>/`

1-b에서 확정한 카피를 그대로 사용해 작성한다 (스크린샷 카피와 톤 일치 필수).

**App Store** (`appstore.md`):
| 항목 | 제한 | 비고 |
|---|---|---|
| 앱 이름 | 30자 | |
| 부제 (subtitle) | 30자 | 검색 가중치 높음 |
| 프로모션 텍스트 | 170자 | 심사 없이 수시 변경 가능 |
| 설명 | 4000자 | 첫 3줄이 접힘 위 노출 — 훅을 앞에 |
| 키워드 | 100자 | 쉼표 구분, 공백 없이, 앱 이름/부제 단어 중복 금지 |

**Play Store** (`playstore.md`):
| 항목 | 제한 |
|---|---|
| 제목 | 30자 |
| 짧은 설명 | 80자 |
| 전체 설명 | 4000자 |

- 글자수 제한은 하드컷이다. 작성 후 각 항목의 글자수를 세어 파일에 `(NN/제한)` 형태로 병기하고 초과분은 즉시 줄여라.
- 로케일이 여러 개면 번역이 아니라 로케일별로 자연스럽게 다시 써라.

### 3. 화면 캡처 → `store_assets/screens/`

1단계에서 매핑한 화면을, **0단계 프리플라이트에서 확정한 경로**(실기기 / 에뮬레이터 / 수동)대로 캡처한다. 각 경로 상세:

1. **Android 기기/에뮬레이터 연결 시** (`adb devices`로 확인):
   ```
   adb exec-out screencap -p > store_assets/screens/<name>.png
   ```
   화면 이동이 필요하면 `adb shell input tap X Y`, `input swipe`, `am start -n <activity>`로 네비게이션. 각 캡처 전 `read`로 이미지를 열어 올바른 화면인지 확인.
2. **연결 기기가 없거나 데모 데이터가 빈약하면 — 에뮬레이터 + 데모 데이터 주입** (도란 실측 검증): ① `flutter build apk --debug` → 에뮬레이터 설치 ② 로컬 DB 스키마를 코드에서 파악해 **데모 데이터 DB를 python sqlite3로 통째로 제작** (한 달치, 감정/상태 다양하게 — 각 카피의 증거가 되는 대화·기록을 연출, 짧은 히어로 대화 필수) ③ `adb push` + `run-as <pkg> cp databases/...`로 교체 (debug 빌드만 가능, `PRAGMA user_version` 맞출 것) ④ 에뮬레이터는 데모 모드 상태바(9:41)가 정상 작동 ⑤ 상태바·네비는 렌더러 `crop`으로 제거하고 **전 캡처 동일 종횡비**로 맞춘다. 긴 한글 스크립트는 bash heredoc이 깨질 수 있으니 write 도구로 .py 파일을 만들어 실행할 것. 실사용자 기기에는 데모 데이터를 절대 주입하지 않는다 (병합 오염).
2-b. **캡처는 되지만 화면이 빈약하면(설정·프로필·폼·조밀한 리스트) — raw 프레이밍 금지, 디자인 목업으로**: 그대로 프레임 씌우면 세트가 싸 보인다(towniemap 실측 — store_assets 설정화면 실패). 핵심 기능을 마케팅용으로 재디자인한 HTML/CSS 목업(듀얼 별점바·3D 아이콘·CTA 버튼·리스트 썸네일)을 만들어 캡처하거나(towniemap `store-screenshots/build_shot.py` 경로 참조), 여의치 않으면 개념 슬라이드(4번)로 대체한다. 판단 기준은 `PATTERNS.md`의 "제작 경로" 절.
3. **둘 다 불가하면**: 사용자에게 필요한 화면 목록(1단계 매핑)을 제시하고 수동 캡처를 요청. iOS 시뮬레이터 캡처는 Mac 전용(`xcrun simctl io booted screenshot`)임을 안내.
4. **캡처가 불가능/무의미한 포인트 → 화면 없는 개념 슬라이드 (codex 생성)**: 아직 빌드 안 된 기능, 존재하지 않는 화면, 어떻게 해도 빈 화면(empty state)뿐인 포인트는 앱 화면 대신 **5단계에서 codex로 개념 이미지를 생성**해 '포인트 자체를 이미지로' 표현한다(brand-hero형). 가드레일: ⓐ **생성 이미지에 앱 UI를 위조·재구성 금지**(심사 리젝) — 개념·라이프스타일·상황 비주얼만. ⓑ 스토어 규격상 세트에는 **실제 UI 캡처가 최소 1장 이상** 있어야 하므로 화면 없는 슬라이드는 세트 일부만(주로 1번 훅 슬롯). ⓒ 텍스트는 렌더러가 얹는다. → 1단계 표의 '캡처' 칸에 이런 포인트는 `개념(codex)`로 표기한다.
- 상태바가 지저분하면(시계/배터리) 캡처 전 데모 모드 권장: `adb shell settings put global sysui_demo_allowed 1` 후 demo mode 커맨드.

### 4. 렌더링 → `store_assets/output/`

- **스타일 티어 선택**: 같은 폴더의 `PATTERNS.md`(실측 기반 — 무료 4티어·유료 3패턴·카테고리별 문법·카피 원칙·세트 QA 규칙)를 읽고 앱 성격에 맞는 티어와 카피 문법을 골라 사용자에게 제안한다.
- `store_assets/config.yaml` 작성. 스키마는 `${CLAUDE_PLUGIN_ROOT}/skills/store-shots/config.example.yaml` 참조. 1-b에서 확정·감사 통과한 title/subtitle을 그대로 사용.
- 배경 그라데이션은 앱의 브랜드 컬러(테마/스플래시에서 추출)를 기본으로.
- 실행:
  ```
  python ${CLAUDE_PLUGIN_ROOT}/skills/store-shots/generate.py store_assets/config.yaml
  ```
- **세트 QA (필수)**: 렌더 후 **전 컷을 스트립으로 붙여**(`marketing/storefront-preview.png` 생성) 나란히 검증 — 낱장으론 일관성을 못 잡는다. 체크: ① 텍스트 잘림/대비 ② **화면-카피 정합** (이 화면이 이 카피의 증거인가) ③ 같은 캡처 재탕 없는가 ④ 뱃지 남발 없는가 (절반 이하) ⑤ 위젯형 화면의 빈 하단 노출 없는가 ⑥ 단일 지오메트리 시스템인가 (일관성 > 리듬). 하나라도 걸리면 config 수정 후 재실행.

### 5. 마케팅 비주얼 배경 (콘셉트에 따라 codex 생성 또는 절차적 렌더)

**배경 소스 결정 규칙**: ① 배경 콘셉트가 **소품·사진급 연출**(책상 위 소품, 도시 야경, 라이프스타일 신)일 때만 codex 생성을 쓴다 — **미니멀 단색/그라데이션 무드는 절차적 렌더(`glow` + `decor_style: stars`)가 대비·일관성·재현성에서 우월하다** (도란 실측: codex 사진 배경이 오히려 대비를 해침). ② **codex 유무는 0단계 프리플라이트에서 확정**; 미감지·생성 3회 실패 시에도 절차적으로 폴백. 렌더러는 두 경로 모두 지원하므로 config만 다르다.

**원칙 (스토어 정책·생성기 한계):**
- **앱 UI는 반드시 실제 캡처**만 쓴다. 앱 화면·인터페이스를 생성·재구성하면 심사 리젝 사유다. 생성 이미지는 배경·연출·소품 컨텍스트 또는 **앱 UI가 없는 개념 슬라이드**(brand-hero형)만 담당하며, **세트에는 실제 UI 캡처가 최소 1장 이상** 있어야 한다(스토어 규격).
- 생성 프롬프트에 **텍스트/글자 렌더링을 절대 포함하지 않는다** (한글은 100% 깨진다). 모든 문구는 렌더러가 얹는다.

**절차:**
1. 마케팅 포인트별 배경 콘셉트를 정한다 (예: 감정일기 → 달빛 밤하늘, 가계부 앱 → 아늑한 저녁 식탁, 지도 앱 → 항공뷰 도시 보케).
2. Fable 5급 기준으로 프롬프트를 작성한다 — brtimg 하네스가 있으면 `/brt:img-prmpt build`로, 없으면 그 규약대로 직접: 구도·조명(색온도/방향)·질감·색 팔레트(브랜드 hex 명시)·무드 전부 명시, 세로 비율, 상단 1/3은 텍스트 오버레이용 여백(low-detail) 지시, "no text, no letters, no logos" 필수.
3. **codex CLI로 생성** — codex는 내장 `image_gen` 스킬을 가지므로 워킹디렉토리와 저장 경로만 명시하면 생성→검증→저장까지 스스로 처리한다 (실측 검증됨, codex-cli 0.144+):
   ```
   codex exec --sandbox workspace-write -C <앱루트/store_assets> "이미지 생성 도구로 세로 배경 1장을 생성해 marketing/backgrounds/<name>.png 로 저장해라. 프롬프트: <영문 프롬프트>. 생성이 불가능하면 NOIMAGE 라고만 출력해라."
   ```
   출력에 NOIMAGE가 있거나 파일이 없으면 폴백으로 전환한다.
4. 생성 결과를 `read`로 멀티모달 검증: 글자 아티팩트, 왜곡된 사물, 상단 여백 확보, 브랜드 컬러 조화. 미달이면 프롬프트 수정 후 재생성 (최대 3회, 그래도 미달이면 그라데이션 폴백).
5. `config.yaml`의 해당 screen에 `background_image: marketing/backgrounds/<name>.png` + `overlay`(텍스트 대비용, 기본 0.35)를 지정하고 4단계 렌더링을 재실행한다.
6. **이미지별 설명 작성** → `store_assets/marketing/captions.md`: 각 최종 이미지마다 파일명, 스토어 슬롯(몇 번째 스크린샷), 대응 마케팅 포인트, 화면 속 카피, 배경 콘셉트와 의도, 생성 프롬프트 요약을 기록한다. 이 파일이 스토어 업로드 순서의 기준이다.

**개념 슬라이드(화면 없는 포인트 이미지) 렌더:** 3단계 4번으로 `개념(codex)` 표기된 포인트는 배경이 아니라 **슬라이드 전체가 생성 이미지**다. 위 절차와 동일하게 프롬프트 작성·생성·검증하되, 프롬프트에 앱 UI 배제를 명시("no app UI, no phone screen, no interface, no text")하고, config의 해당 screen에서 **`source`를 생략**하고 `background_image`만 지정한다 — 렌더러가 풀블리드 이미지 위에 뱃지·헤드라인·서브만 얹는다(디바이스 합성 없음). `overlay`(0.35~0.5)로 텍스트 대비 확보.

**스토어 밖 배너 (OG·소셜·PH 갤러리·스토리) — `banners:` 섹션:** 렌더러 config 최상위 `banners:`에 임의 사이즈를 선언하면 가로·정사각은 피처그래픽 레이아웃, 세로는 스크린샷 레이아웃으로 렌더된다(`config.example.yaml` 참조). **경계 규칙**: ⓐ 스토어 심사 대상이 아니므로 배너 비주얼은 생성 이미지(제품 사진 레퍼런스 + GPT Image 2/codex) 자유 — "UI 위조 금지"는 스토어 스크린샷 세트에만 적용된다. ⓑ 단, 한글 문구는 배너에서도 반드시 렌더러가 얹는다(생성기 한글 깨짐). ⓒ 카피·팔레트·폰트는 스크린샷 세트와 공유해 브랜드 일관성을 유지한다.
