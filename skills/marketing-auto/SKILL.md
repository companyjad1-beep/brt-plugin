# marketing-auto — 마케팅 자동화 하네스

앱/서비스 프로젝트 루트에서 실행한다. 상태는 전부 대상 프로젝트의 `docs/marketing/`에 남는다.

**북극성**: 콘텐츠 한 편의 최종 판정 기준은 하나 — **"이 글을 본 독자가, 우리가 정한 그 행동을 할 이유가 글 안에 있는가."** 이유가 없으면 아무리 잘 쓴 글도 기각이다. 이 스킬의 전신(marketing-plan)은 목적 없는 글·회사 소개글을 만들어서 폐기됐다. 같은 실패를 구조로 막는다:

1. **목적 게이트** — 모든 콘텐츠는 생산 **전에** 목적과 CTA를 선언하고, 완성 **후에** 그 기준으로 채점된다.
2. **주제 집계·삼각측량** — 감이 아니라 실측 집계(합산·건수·중앙값)로 후보를 만들고, 세 근거의 교집합만 주제가 된다(시의 각도만 ②증명 면제 — research.md §1). [research.md](research.md)
3. **성과 순환** — 게시 결과를 수집·분석해 골격과 주제를 승격/도태시킨다. 돌수록 우리 채널에서 먹히는 것만 남는다.

## 모드

| 모드 | 하는 일 | 문서 |
|---|---|---|
| **write** (기본) | 채널 공용 신규 리서치 → 의미 중복 차단 → 편별 사실팩 → 채널별 자동 생산. 요청 1회가 run이며 날짜 경계 없음. 채널 미지정은 쓰레드 | 이 문서 + research.md (+ threads-ops.md: 쓰레드 분기만) |
| **batch** (명시 요청) | 주제 선정 → 배치표 승인 → 훅 승인 → 채널별 생산 | 이 문서 + research.md (+ threads-ops.md: 쓰레드 분기만) |
| **recycle** (명시 요청) | report가 추천한 땔감 1편을 새 첫 줄·종결·형태로 재발행 준비 | 이 문서 + report.md (+ threads-ops.md: 쓰레드 분기만) |
| **collect** | 브라우저로 4채널 통계 순회, 게시물별 지표를 장부에 기록 | [collect.md](collect.md) |
| **report** | 장부 분석 → 뭐가 먹혔나 → 골격 승격/도태 + 다음 배치 권고 | [report.md](report.md) |
| **engage** | 댓글 원정 — 오늘 뜨는 도메인 글을 찾아 페르소나 일치 답글 초안을 만든다 (남의 도달에 올라타는 초기 성장 지렛대) | 아래 §engage |
| **publish** | **미구현 예약석.** 요청받으면 "아직 없음, 게시는 수동"이라고 답한다 | — |

`write`는 `brtwritenotai write`와 다른 `marketing-auto` 내부 오케스트레이션 이름이다.

## write 파이프라인

일반 write는 승인 없이 아래 12단계를 끝까지 진행한다. 사용자가 `주제부터 보여줘`를 명시한 경우에만 6단계 후보표에서 멈추고 응답을 기다린다.

| 단계 | 계약 |
|---|---|
| 1 run 시작 | 요청 1회에 `run_id`를 만들고 요청 편수(미지정 1편), 선택적 사용자 지정 주제, 요청 채널(미지정 쓰레드)을 확정한 뒤 playbook.md와 ledger.md를 로드한다. 기존 주제 활용이 명시되면 `topic_pack_id`를 먼저 찾는다. |
| 2 신규 발견 리서치 | 신규 주제면 이번 run의 최근 반응 글·실질문·검색 수요·시의 사건을 채널 공용으로 새로 수집한다. 기존 주제팩 파생이면 신규 주제를 선정하지 않는다. |
| 3 포지셔닝 필터 | 계정 포지셔닝 밖 후보를 제외한다. |
| 4 삼각측량 | 수요·증명·우리 재료를 대조한다. 시의 각도는 기존 증명 면제를 유지한다. |
| 5 의미 중복 게이트 | 신규 write는 ledger의 완성 초안·게시 글, 모든 주제팩, 이번 run의 `selected_signatures`를 의미 서명으로 대조한다. 명시적 채널 파생만 아래 예외를 적용한다. |
| 6 후보 확장 | 통과 후보가 부족하면 검색 토큰·출처·기간을 넓히고, 그래도 부족하면 검증된 미달을 보고한다. |
| 7 주제팩·편별 사실팩 | 신규 통과분은 공용 주제팩을 저장하고, research.md §0의 `fact_pack` 필드를 편별로 채워 사실 검증을 각각 수행한다. 파생은 같은 주제팩의 변동 사실을 재검증한다. |
| 8 채널별 레퍼런스·자동 훅 선택 | 제작 시점의 요청 채널 최신 상위 글·골격·훅을 새로 수집하고 사실팩을 기준으로 훅을 선택한다. |
| 9 봉인된 작가 생산 | 편별 사실팩으로 본문을 생산한다. |
| 10 목적·AI 티·중복·잔존 검수 | 완성본을 네 게이트로 검수한다. |
| 11 ledger 기록 | 의미 서명·`topic_pack_id`·파생 관계·리서치 근거를 포함해 완성 초안을 기록한다. |
| 12 본문·선택 훅 근거·대안 훅 2개·출처·중복 결과 출력 | run 결과를 한 번에 출력한다. |

### 공용 주제팩과 채널별 파생 제작

- 채널을 생략한 일반 새 글 요청은 쓰레드로 제작한다.
- 채널을 명시한 신규 write는 같은 공용 주제 리서치 뒤 해당 채널 파이프라인으로 보낸다.
- "이 주제로 인스타 카드뉴스도", "이 주제로 블로그도"처럼 기존 주제 활용을 명시하면 신규 주제 선정이 아니라 주제팩 파생 제작이다.
- 파생 제작은 같은 의미 서명을 허용하되 동일 topic_pack_id를 유지하고 사용 채널을 추가한다.
- 가격·정책·시세·제품 사양 같은 변동 사실은 파생 시점에 다시 검증한다.
- 각 채널의 최신 상위 글·골격·훅은 제작 시점에 새로 수집한다.
- 공유하는 것은 사실·출처·우리 재료뿐이며 이전 채널의 본문·문장·훅은 작가 번들에 넣지 않는다.
- 같은 주제팩을 같은 채널에서 다시 만드는 것은 신규 write가 아니라 명시적 recycle 또는 사실 변경 재작성이다.
- threads-ops.md는 쓰레드 제작에만 적용한다.

파생 분기는 재검증한 공용 사실·출처·우리 재료로 현재 편의 `fact_pack`을 새로 만들고, 요청 채널에서 수집한 골격과 함께 기존 봉인 규칙대로 작가에게 넘긴다. 이전 채널 산출물은 검색하거나 상속하지 않는다.

## playbook.md — 첫 실행 게이트

`docs/marketing/playbook.md`가 있으면 읽고 넘어간다. 없으면 여기서 만든다:

1. **자동 추론** — `docs/PRD.md`·`docs/BRAND.md`·`docs/MARKETING.md`(구버전 산출물이 있으면 재료로만)·README·코드베이스를 읽고 아래 표의 초안을 채운다.
2. **미니 인터뷰(3~5문)** — 추론으로 못 채우거나 판단이 필요한 칸만 묻는다. 추론 결과 표를 먼저 보여주고, 남은 질문은 선택지형이면 **한 번에 최대 4문 일괄**(AskUserQuestion 다중 질문), 앞 답에 따라 갈리는 질문만 순차로. 다 채워져 있으면 "이렇게 추론했다" 확인 한 번만.

| 항목 | 내용 |
|---|---|
| 제품 한 줄 | 무엇을 누구에게 |
| 목적 우선순위 | 검색유입 / 팔로워 / 전환(설치·가입) 중 이 프로젝트의 순서 |
| 계정 전략 | 기본값: 피드형(쓰레드·인스타·쇼츠)=퍼스널 계정(빌드인퍼블릭 서사), 네이버 블로그=주제별 분리(SEO 주제 일관성). 프로젝트별로 덮어쓰기 가능. **혼합 계정 규칙**: 쓰레드는 도달이 글 단위(실측 r=-0.19)라 주제 혼합이 도달을 안 깎는다 — 깎이는 건 프로필 전환이므로 바이오 한 줄이 콘텐츠 묶음을 설명해야 한다("만드는 사람" 류). **서비스 계정↔퍼스널 이원 운영 시**: 서비스 계정이 본진, 퍼스널은 인용 리포스트(한 줄 코멘트)로 개인 서사에 맞는 글만 증폭. 쓰레드 바이오(IABA 4줄)·고정글 설계는 [threads-ops.md](threads-ops.md) §4 |
| 페르소나 참조 | **계정 단위 화자 카드 파일 경로** (계정당 1개 — 여러 프로젝트가 공유. 없으면 확인된 사실로 생성 제안). 페르소나는 지어낸 캐릭터가 아니라 실존 사실만으로 조립하고, 생산 때 playbook과 함께 작가에게 반드시 전달한다 — 1인칭 장면은 이 카드의 사실 풀에서만 꺼낸다 |
| 채널 | 운영 채널 + 명시적 제외 채널 |
| 재료 금고 | 오리진(왜 만들었나 — 날짜·사건까지)·현장 디테일·내부 수치·강점 목록(기능명 ❌, "그래서 뭐가 풀리나"로 ⭕) |
| 말투 | **① 플랫폼에 맞춘다** — 한 말투를 전 채널에 강제하지 않는다. voice 카드·BRAND 보이스는 화자 정체성(사실·태도)이지 종결어미가 아니다 — 종결·어휘는 채널 관습이 정한다(쓰레드=구어체·감정부호, 네이버 블로그=해요체 설명, 인스타·쇼츠=짧은 구어). 그 채널 상위 글이 쓰는 말투가 근거다. **② 쉽게 말한다** — 일상 대화에서 안 쓰는 한자어·문어체·전문용어 금지(예: 구매하다→사다, 진행하다→하다, 하자담보책임→"고장 나면 물어주는 것"). 어려운 개념은 용어 대신 예시·장면으로 푼다. 그 외: BRAND 보이스 있으면 재사용, 없으면 대상 프로젝트의 `_workspace/brtwritenotai/voice-card.md`(brtwritenotai voice 모드 산출물)를 참조. 둘 다 없으면 말투 칸을 비워 두고 생산 때 작가에게 "voice 카드 없음"으로 전달한다 |

게이트: 재료 금고의 오리진이 "우리가 겪어봐서 안다" 수준으로 구체적이지 않으면, 그 재료를 쓰는 주제는 후보에서 뺀다(지어내지 않는다).

`docs/marketing/topics.md`가 없으면 여기서 **빈 표(덩어리 × 고백·해부·정보·논쟁·시의)로 생성**한다 — 3단계가 읽을 파일이 없으면 매 배치가 리서치 0에서 다시 시작한다.

## batch 파이프라인

**0. 시작 전 이 문서와 research.md를 Read로 다시 읽는다. 기억으로 돌리지 않는다.** 그리고 아래 표를 그대로 출력하고 칸을 채우며 진행한다:

| 단계 | 산출물 | 비고 | 완료 |
|---|---|---|---|
| 1 playbook 로드/생성 | 설정 확정 | | ☐ |
| 2 report 반영 | 이전 성과 가중치 (첫 실행이면 생략) | | ☐ |
| 3 주제 집계·삼각측량 | 집계표 + 삼각측량 후보표 + topics.md 갱신 | | ☐ |
| 4 배치표 | 주제×채널·형태×목적×CTA×골격 | **승인 지점 ①** — 사용자 승인 없이 생산 금지 | ☐ |
| 5 레퍼런스·골격 | 채널별 골격 (라이브러리 재사용 우선) | | ☐ |
| 6 생산 | 편별 훅 후보 2~3개 → 선택된 훅으로 본문 확정 | **승인 지점 ②** — 훅 선택. 장면 재료 없으면 사용자 질문 | ☐ |
| 7 목적 게이트 | 편별 채점, 기각분 재생산·폐기 | 기각 시 재생산 1회 루프, 재실패면 폐기 | ☐ |
| 8 장부 기록 | ledger.md 행 추가 + 본문 전문 채팅 출력 | | ☐ |

승인 지점은 4단계(배치표)와 6단계(훅 선택) **두 번**이다. 둘 다 사용자 응답을 받고 넘어간다.

1. **playbook 로드/생성** — 위 게이트.
2. **report 반영** — `ledger.md` 하단의 **최신 `## 리포트` 섹션**을 열어 성과가 좋았던 **형식·훅·길이·CTA·골격**의 가중치와 주제 방향의 **검색 토큰**만 반영한다. 리포트는 과거 주제를 직접 선정하거나 자동 재생산하지 않는다. 사용자가 직접 준 주제의 검증 예외를 제외하고, 실제 주제 후보·선정은 3단계의 **현재 리서치** 집계·삼각측량에서 하고 4단계 배치표 승인을 거친다. 리포트 섹션이 없으면 생략한다(여기서 report.md를 로드해 분석을 다시 돌리지 않는다 — 분석은 report 모드의 일이다).
3. **주제 집계·삼각측량** — [research.md](research.md) §1을 그대로 밟는다:
   1. `docs/marketing/topics.md`를 Read한다 — 백로그에서 먼저 꺼낸다.
   2. 백로그가 얇으면 §1 집계를 돌린다(합산 · 건수 · 중앙값, 원포스트 지배 행은 `아웃라이어 주의` 표기).
   3. [덩어리×각도] 매트릭스로 각도를 분화한다.
   4. 삼각측량으로 거른다 — 통과분만 후보표에 올린다. 새로 나온 덩어리·각도는 topics.md에 적립한다.

   사용자가 주제를 직접 줬으면 집계를 건너뛰고 **검증만** 한다(수요 근거·재료 근거가 있는지 — 없으면 그대로 말하고 대안 제시).
   **batch 재사용 체크(자동)**: 후보를 ledger.md의 기존 행과 대조한다. 분류 단위는 **[덩어리×각도]** — 이전 배치가 쓴 덩어리는 후순위지만 **각도가 다르면 통과**한다. 덩어리·각도가 둘 다 같으면 기본 제외이고, 다시 쓰려면 배치표 골격 칸에 `재사용: 골격·각도 변경`을 명시해 사용자 눈에 보이게 한다. 이 분류는 batch 승인용이며 write의 의미 중복 게이트를 대신하지 않는다. 사용자가 중복을 기억해서 알려줄 필요가 없어야 한다.
4. **배치표 승인** — 표로 제시하고 사용자 승인 1회. 승인 없이 생산 금지.

   | 덩어리×각도 | 채널·형태 | 왜 (채널·형태 근거) | 목적 | CTA 한 문장 | 골격 (표본 N개) | 도달 3축 | 연쇄 |
   |---|---|---|---|---|---|---|---|

   **연쇄 칸** — `단발` 또는 `⭕ + 2번 홀드백 한 줄`을 적는다(research.md §3 연쇄 규칙). 홀드백 재료가 실사실로 확보돼 있는지까지 여기서 판정한다 — 미확보면 단발로 내린다.

   **도달 3축 점검 (research.md §3 — 가설 단계, 게이트 아님)** — 편마다 `시제(진행형) / 반전(첫 3줄) / 화자 위치(당사자)`를 ⭕❌로 적어 사용자가 보고 판단하게 한다. 3축은 표본 2의 가설이고 성공 풀이 부분 반증한다(과거 완결·관찰자 화자도 터짐) — 편성 금지 근거로 쓰지 않는다. 확정 실측은 별개다: 도달과 반응은 분리 판정(§3), 장문 벽글·회고 후속은 배포가 안 붙는다.

   골격 칸에는 **재사용 골격 ID + 해부 표본 수**를 적는다(예: `th-피해-06 (표본 12)`). 아직 해부 전이면 `신규 해부 예정(5단계)`이라고 적고, 5단계 해부 결과가 배치표에 적은 형태·치수와 달라지면 **그 행만 다시 확인받는다**(배치표 전체 재승인은 아니다). 표본이 20개 미만이면 그 사실이 배치표에 보여야 한다 — 표본 없이 대표 원문 1~2개에서 딴 골격은 골격이 아니라 인상이다(2026-07-29 실측: 규칙은 문서에 있었는데 실행이 건너뛰었다).

   - 채널·형태 칸은 `쓰레드 / 장문 서사형`처럼 둘을 함께 적는다. 형태 목록과 치수는 research.md §3 형태 표.
   - 첫 칸은 주제 한 줄이 아니라 `덩어리 × 각도`로 적는다(예: `선입금 잠수 × 고백`) — 중복 체크 단위와 같아야 대조가 자동으로 된다.
   - "왜"는 research.md §2 매칭 규칙(채널)과 §3 형태 표(형태→목적 짝)로 채운다. 그 덩어리가 집계표에서 `아웃라이어 주의`였으면 **근거 칸에 그 사실을 반드시 표기**한다(순위 근거가 아닌 걸 순위처럼 읽히게 두지 않는다).
   - 같은 주제를 두 채널에 실으면 행을 두 개로 — 복붙 금지, 채널별 골격으로 각각 만든다.
   - 규모 기본값: 채널당 1~2편. 편수 요청에 파이프라인을 양보하지 않는다 — 제대로 된 3편이 대충 만든 10편보다 낫다고 먼저 말한다.
5. **레퍼런스·골격** — `skeletons.md`에 그 채널·도메인의 살아있는 골격(도태 안 된 것)이 있으면 재사용. 없으면 research.md §3(글)/§4(영상)로 새로 해부해서 라이브러리에 추가.
   **신선도 규칙**: 골격을 재사용하는 배치라도 **매 배치 최소 1회는 그 채널·도메인의 최신 상위 글을 새로 수집**해 훅 구조·부품을 라이브러리에 보충한다 — 수집이 멈추면 스왑 소스가 늙고 같은 훅만 반복된다.
   **실패 대조군**: 성공 풀만 뜨지 말고 같은 주제로 **안 터진 글**을 함께 떠서 대조한다(research.md §3). 같은 계정이 같은 사건으로 쓴 두 글의 성패가 갈린 사례를 찾으면 최우선 해부 — 계정·도달이 통제된 자연실험이다.
   **동종 계정 확인**: 같은 포지셔닝의 경쟁 서비스 계정을 찾아 성과를 본다. 그쪽이 이미 우리 계획을 실행했다면 그 결과가 우리 예측보다 강한 근거다 — 배치표를 그에 맞춰 고친다.
6. **생산** — 문장은 전부 **brtwritenotai 스킬(`/brt:write-notai`)**로 쓴다(채널 규약·AI티 게이트 포함, 여기서 재구현 금지). 이미지·영상 프롬프트는 **brtimg 스킬(`/brt:img-prmpt`)**로 만든다. 쇼츠 1편 = 훅 대사 + 초 단위 장면 스크립트 + 장면별 brtimg 영상 프롬프트.
   **인스타 카드뉴스**: HTML(1080×1080)→렌더(Playwright)로 만든다. 훅·반전 카드는 타이포만 쓰지 말고 **장면 재현**(이체 다이얼로그·영수증·채팅 UI 목업)으로 — "증거는 캡처가 이긴다"(research.md §3)의 디자인 적용이다. 정보·리스트 카드는 타이포 유지(전 장이 장면이면 피로). 2026-08-02 실전: 타이포 8장 초안이 밋밋 판정 → 핵심 3장 장면 재현 교체.

   **작가 분리 (세션 1개 금지)** — 지휘 세션이 본문을 직접 쓰지 않는다. 편(또는 채널) 단위로 **서브에이전트(새 컨텍스트)를 작가로 띄우고**, 아래 핸드오프 번들**만** 전달한다 — 지휘 세션의 수집·기획 맥락을 통째로 물려주지 않는다. 이유 둘: ① 컨텍스트가 크면 작가 규칙(양화·음화·치수)이 밀려서 조용히 드롭된다 ② 직전 산출물의 오류 패턴이 다음 편에 상속된다(같은 원리의 실측: brtimg storyboard "새 채팅이 기본", blind-judge 세션 분리). 서브에이전트를 못 띄우는 환경에서만 예외 — 그땐 편 사이에 핸드오프 번들을 다시 Read해서 컨텍스트를 리셋한다.

   **작가에게 넘기는 것**(빠뜨리면 골격만 있고 재료 없는 글이 나온다): playbook에서 추출한 현재 편의 계정·채널 규칙 + 페르소나 카드에서 추출한 현재 편의 사실 + voice 카드(있으면) + research.md §0의 편별 `fact_pack` + 골격(치수 포함). 이 묶음이 봉인된 핸드오프 번들이다.

   이전 초안·직전 편 본문은 번들에 절대 포함하지 않는다. 작가는 전체 ledger·batches·topics·이전 본문을 검색하지 않고, 편별 fact pack과 추출된 골격만 읽는다. "참고용" 이전 본문도 오류 패턴과 사실을 오염시키므로 금지한다. write는 편마다 새 작가 컨텍스트를 사용한다. 서브에이전트를 못 띄우면 편 사이에 해당 편의 fact pack을 다시 읽어 컨텍스트를 리셋한다.

   **재작성 게이트**: 주제·제품·예시·사실이 바뀌는 재작성은 수정이 아니라 새 편 생산이다. 새 작가 컨텍스트와 새 fact pack을 만들고, 목적·CTA·승인된 골격·말투만 유지한다. 이전 편의 사실·수치·사례·문장은 모두 무효다. 현재 주제 재료가 없으면 질문하거나 후보를 교체하며 이전 초안으로 빈칸을 채우지 않는다. 말투·길이·표현만 바뀌고 사실이 그대로일 때만 인라인 polish를 허용한다.

   **훅·재료 분기**:
   - write: 우리 채널 성과 → 이번 수집 상위 글 → 활성·승격 골격 순으로 훅을 자동 선택하고 대안 2개를 출력한다.
   - batch: 기존 훅 후보 2~3개 사용자 선택 게이트를 유지한다. 편마다 후보를 먼저 제시하고 사용자가 고른 뒤에 본문을 확정한다.
   - 주제 미지정 write의 재료 부족: 후보를 탈락시키고 다음 후보로 교체한다.
   - 사용자 지정 write의 재료 부족: 주제를 바꾸지 않고 사용자에게 묻는다.
   - batch의 재료 부족: 기존 장면 재료 질문을 유지한다. 골격의 "구체 장면·경험" 칸을 채울 재료가 재료 금고에 없으면 생산 전에 사용자에게 그 자리를 묻는다("이 골격엔 실제 장면이 필요하다 — 겪은 일 하나만").
   - 전 후보 탈락: 부족을 보고하고 과거 사실로 편수를 채우지 않는다.
   - 공통: 1인칭 생활 디테일을 지어내서 채우지 않는다. 부득이 가정으로 썼으면 편마다 `⚠️ 사실 확인 대기`를 붙이고, 사용자 확인 전에는 게시 대기 상태로 두지 않는다.

   **연쇄 게이트**: 형태 치수를 넘는 내용이 생기면 **1번을 늘리지 말고 홀드백으로 내린다**(벽글은 배포가 안 붙는다 — research.md §3). 연쇄는 도달 장치가 아니라 **긴 내용을 도달 안 죽이고 싣는 자리**다. 생산 단계 산출물은 **1번 본문 + 홀드백 지정까지**이고, 2·3번 본문은 반응이 온 뒤 쓴다. 1번은 2번 없이도 완결일 것, 연쇄 마지막 편에 **제품 소개를 붙이지 않을 것**(동종 계정 사망 패턴 ⓒ).

7. **목적 게이트 (편별 채점)** — 채점자는 작가와 별개여야 한다(작가 서브에이전트가 자기 글을 채점하지 않는다 — 지휘 세션 또는 신선한 검수 에이전트가 한다). 하나라도 실패면 기각. 재생산은 1회, 또 실패면 그 편은 폐기하고 이유를 보고한다:
   - **행동 근거**: 배치표의 CTA를 독자가 할 이유가 글 안에 있는가. 특징 나열은 이유가 아니다.
   - **광고 검사**: 우리 제품/강점 분량 20% 이하 + 강점 문단을 지워도 남은 글이 쓸모 있는가. 무너지면 처음부터 광고였다.
     **예외 — 고정글(프로필 앵커)**: 계정당 1편, 프로필 방문자용 소개·전환 글은 제품 설명이 곧 답이라 20% 규칙을 적용하지 않는다. 대신 오리진 고백으로 열고 **한계 인정 1줄**(아직 작다·수치 없다 등 사실)이 반드시 들어가야 한다 — 그게 빠지면 그냥 광고다.
   - **품질**: brtwritenotai 게이트(음화·채점) 통과본인가. 작가에게는 rulebook(음화)만 주지 말고 **양화 기법(rulebook 양화·style-presets)**도 함께 전달한다 — 음화만 주면 슬롭 없는 무미(無味) 글이 나온다.
   - **배치 세로 읽기**: 배치 전체를 이어 읽었을 때 문체 온도가 균일하면 편별로 감정 온도를 재배분한다(전부 담담·전부 비명 둘 다 실패 — 진짜 계정은 날마다 기분이 다르다).
   - **잔존 검사 (재작성 편만)**: 폐기된 이전 주제의 제품명·수치·사례·문장이 남아 있으면 기각한다. 이전 편의 고유명사·숫자 목록을 뽑아 새 본문에서 기계적으로 검색하며 느낌으로 판정하지 않는다. 잔존하면 새 작가 컨텍스트로 1회 재생산하고, 다시 실패하면 해당 편을 폐기한다.
   - **살아있는 한 줄 검사**: 편마다 "스크린샷 찍힐 문장이 하나 있는가"를 묻는다. 없어도 기각은 아니지만 판정을 편 헤더에 정직하게 표기한다 — 축적되면 report가 "살아있는 한 줄 유무 × 성과"를 가른다.
8. **장부 기록·전문 표시** — `ledger.md`에 행 추가. **완성된 편은 파일 경로만 알리지 말고 본문 전문을 채팅에 그대로 보여준다** — 사용자 확인·사실 검증은 채팅 본문 기준으로 받는다. 게시는 사용자가 수동으로 한다. **게시 후 URL을 알려주면 그 행에 기록한다** — URL이 있어야 collect가 지표를 붙일 수 있다.
   **쓰레드 게시 안내**: 쓰레드 제작 분기에서만 편 전달 때 [threads-ops.md](threads-ops.md) §1의 권장 발행 시간대·팀킬 주의를 함께 알리고, 게시 직후엔 §2 60분 루틴(내부 답글 초안 + engage)을 제안한다.

## engage — 댓글 원정

신규·소규모 계정의 확률 전략: 우리 글의 콜드스타트 도달(복권)에만 걸지 않고, **이미 터진 글의 댓글창(확정 노출)**에 올라탄다. 좋은 글 1편보다 좋은 댓글 여러 개가 초기 성장엔 더 확실하다.

1. **표적 수집** — 브라우저로 도메인 검색(우리 채널·도메인 일치)에서 **오늘·최근 뜨는 글** 3~5개를 고른다. 기준: 반응이 붙는 중(댓글 수십+), 우리 페르소나가 실경험으로 보탤 말이 있는 글만. 품앗이·슬롭 글은 제외.
2. **답글 초안** — 편당 1~2문장, `brtwritenotai` 답글 모드로. 규칙: 페르소나 실사실만 / 원글에 실제로 보태는 내용(공감 한 줄만은 금지) / 우리 제품·링크 언급 **절대 금지**(댓글 광고는 계정을 죽인다) / 원글 화자를 가르치려 들지 않는다.
3. **전문 채팅 출력** — 표적 글 요약·URL + 답글 초안을 함께 보여주고, 게시는 사용자가 한다.
4. **기록** — ledger 하단 `## 댓글 원정` 섹션에 날짜·표적 URL·단 댓글·(나중에) 반응을 기록한다. 우리 댓글에 달린 답·프로필 유입 신호는 collect가 함께 본다.

권장 리듬: 배치 사이 매일 3~5개. 글 발행이 없는 날에도 댓글 원정은 돌 수 있다. **발행일엔 발행 후 30~60분 구간에 붙인다** — [threads-ops.md](threads-ops.md) §2 60분 루틴. 내 글에 달린 댓글 답글도 같은 규칙(질문으로 닫아 티키타카 증식)으로 초안을 만든다. 원정 중 발견한 팔로우 대상(대형·동급·고객 신호 유저 — threads-ops.md §2.5)은 리스트로 제안한다(실행은 사용자).

## ledger.md 형식

```markdown
| id | 날짜 | 채널 | 형태 | 주제 | 의미서명 | topic_pack_id | 파생 | 목적 | CTA | 리서치근거 | 훅유형 | 골격ID | 연쇄 | 산출물 | 게시URL | 지표 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 2026-07-29-th1 | 2026-07-29 | 쓰레드 | 장문 서사형 | ... | 독자 문제 \| 핵심 주장 \| 사례·근거 \| 결론 | tp-20260729-01 | 원본 | 팔로워 | ... | 출처 URL·수집일·반응 수치 | 1인칭 고백 | th-피해-01 | ⭕ 홀드백: 신고 이후 진행 | batches/2026-07-29/th1.md | (게시 후) | 07-31: 조회 16만 · 좋아요 12 · 댓글 3 |
```

- `의미서명`과 `리서치근거`는 write의 의미 중복 대조와 사실 추적에 쓴다. **게시URL이 없는 완성 초안도 다음 run의 중복 대조 대상**이며, 게시 여부와 무관하게 ledger에 남긴다.
- `topic_pack_id`는 공용 주제팩과 채널별 산출물을 잇는다. `파생`은 최초 제작이면 `원본`, 명시적 새 채널 파생이면 `<기존 채널>→<새 채널>`로 기록한다. 새 채널 파생은 신규 의미 서명을 만들지 않고 기존 의미서명을 유지한다.
- `연쇄` 칸: `단발` / `⭕ 홀드백: <디테일>` / `2번 게시함(MM-DD)`. **연쇄분은 별도 행을 만들지 않는다** — 성과는 스레드 단위라 지표를 1번 id에 누적한다.
- 지표는 **조회를 먼저** 적는다(도달과 반응을 분리 판정 — research.md §3).

- `형태`는 research.md §3 형태 표의 이름을 그대로 쓴다. `훅유형`은 확정된 훅의 부품 성격(예: 1인칭 고백 / 질문 / 장면 즉입 / 명령·저장 유도 / 금액·숫자)을 짧게 적는다 — report가 훅 유형별로 성과를 가른다.
- 지표 표기 규약: **`MM-DD: 지표명 값 · 지표명 값`** 한 형태로 통일한다(예: `07-31: 좋아요 12 · 댓글 3`). 수집일 스탬프와 함께 **누적**하고, 기존 값은 덮지 않는다 — 표기가 흔들리면 report가 중앙값을 못 낸다.
- 빈 칸은 빈 칸으로 둔다 — 추측값 기입 금지.

## 경계

- 게시(업로드)는 안 한다. publish 모드는 예약석.
- 수치·원문·반응수는 전부 출처와 함께만. 지어낸 질문·추측 지표가 문서에 들어가면 이 스킬은 실패다.
- 로그인이 필요한 페이지에서 로그인돼 있지 않으면 시도하지 않고 스킵·보고한다.
